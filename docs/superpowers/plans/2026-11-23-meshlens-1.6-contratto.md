## 0. Regole generali (valgono per tutti i WP)

1. **Proprietà dei file** (§9): un WP modifica solo i file che possiede, crea file nuovi solo nei propri nomi, e nei file condivisi solo nei punti e nel modo descritti in §10. Nessun WP (tranne WP6, che arriva dopo l'unione) tocca un file "congelato".
2. **Schema del database**: lo schema 7 è completo e definitivo (§1). Nessun WP aggiunge tabelle, colonne o indici. Se manca qualcosa → integratore.
3. **Impostazioni**: tutte le chiavi nuove sono in §2 con valore predefinito e validazione già scritte da WP0. Nessun WP tocca `S/settings.py`, `S/secretbox.py`, `W/lib/settings.ts`.
4. **Rotte**: solo nel proprio modulo `api_*.py` (§5), con i prefissi riservati (§5.3). Ogni rotta che scrive usa `dependencies=[Depends(require_auth), Depends(require_json)]` (anche senza corpo utile: il client manda `{}`); le azioni distruttive vogliono `{"confirm": true}` (400 altrimenti); i dati segreti (PSK, URL webhook) escono solo verso il loopback (`is_loopback_request`, §5.2).
5. **Contratti JSON solo additivi**: le risposte e gli eventi WS esistenti non perdono né rinominano campi.
6. **Segreti**: mai nei log (anche a livello DEBUG), nelle esportazioni dei profili, nei messaggi d'errore, negli eventi del bus, nei webhook. Segreti noti: password/PSK/chiavi extra dei broker, `update_token`, `telegram_token`, `webhook_url`, PSK dei canali radio, `security.*` delle radio, `network.wifi_psk`, `mqtt.password` delle radio, `guest` PIN. Per ripulire un testo: `settings.scrub_text(text, *segreti)`.
7. **Invio automatico**: l'unico mittente automatico è il bot di WP5, solo sui bersagli scelti (`bot_targets`), solo testo (`TEXT_MESSAGE_APP`), sempre attraverso `RadioManager.send` / `MqttSender.send` (eredita lock, conferma pubblica e limiti). Mai `override_duty_cycle`, mai scrittura diretta su paho o sull'interfaccia radio. Nessun altro WP pubblica su MQTT o trasmette in radio senza un'azione esplicita dell'utente.
8. **Messaggi d'errore del server in italiano**, con traduzione inglese nel proprio frammento `W/lib/i18n/server-en/wpN.json` (§8.3). `T/test_i18n_catalog.py` deve restare verde.
9. **Connessione SQLite principale (`ctx.conn` / `rt.store.conn`) solo dal thread del loop.** Letture pesanti: `api_data.run_read(ctx, fn)` (connessione in sola lettura in un thread). Scritture dal loop: dopo una scrittura in una rotta chiamare `ctx.conn.commit()`; le scritture fatte dentro gli agganci (§4) vengono salvate dal commit periodico di 1 s (si può comunque fare commit).
10. **Niente lavoro lungo dentro gli agganci** (§4): sono chiamati in modo sincrono sul loop durante l'ingestione. Rete, file, attese → `asyncio.get_running_loop().create_task(...)` o `asyncio.to_thread`.
11. **B1 fuori ambito** (repo aggiornamenti modificabile dalla rete): non si tocca `update_repo`/`update_token`.
12. **Nessuna dipendenza Python nuova.** Dipendenze npm nuove: solo WP4 e solo se indispensabile (QR), con `THIRD_PARTY_NOTICES.md` e `tools/gen_licenses.py` aggiornati (file di WP4 in 1.6).
13. **Test**: ogni WP crea i propri file di test (`T/test_<modulo>.py`, `W/lib/<modulo>.test.ts`); i test esistenti di file che il WP non possiede non si modificano. Radio vere mai: `T/test_radio.py::FakeIface/FakePubSub/FakeNode`, `T/test_radio_manager.py::FakeConnector/FakeHub`, `T/test_app.py::FakeConnector`, `T/helpers.py::make_envelope` si importano in sola lettura. I subagent eseguono solo test mirati; suite complete a fine fase.
14. **Interfaccia**: italiano primario + inglese, solo `t()`/`tn()` (nessun testo letterale nel markup: `W/lib/i18n/scan.test.ts`), token di design esistenti, `W/lib/ui/*` (Card, Button, Field, Switch, Segmented, Modal, Banner, Empty...), aree ≥ 44 px su telefono, testo ≥ 14 px, Svelte 5 runes.
15. Commit in italiano, stile `feat(server): …` / `feat(web): …` / `test: …`.

## 1. Database — migrazione 7 [WP0]

`S/db.py`: `SCHEMA_VERSION = 7`, `_STEPS[7] = _migration_7`. Come le migrazioni esistenti: gira dentro la transazione di `_run_migrations` (`BEGIN` … `PRAGMA user_version=7`), è idempotente (rieseguita su un database già a 7 non cambia nulla e non fallisce), niente `executescript` (farebbe commit), istruzioni eseguite una per una da una **tupla** di stringhe (non con `split(";")`: i corpi dei trigger contengono `;`). Prima della migrazione di un database esistente il backup automatico resta quello di `connect(before_migrate=...)`.

### 1.3 Indice di ricerca dei messaggi (E2/E4): FTS5 con ripiego LIKE

Decisione: **FTS5 a contenuto esterno** se il modulo è compilato nel SQLite in uso (vero nel `.venv` attuale: SQLite 3.49.1 con `ENABLE_FTS5`; il pacchetto PyInstaller usa lo stesso `_sqlite3`), altrimenti **LIKE** sul testo. Nessun dato duplicato oltre all'indice.

Oggetti (creati solo se FTS5 è disponibile):

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts USING fts5(
  text, content='messages', content_rowid='rowid',
  tokenize='unicode61 remove_diacritics 2');
CREATE TRIGGER IF NOT EXISTS messages_fts_ai AFTER INSERT ON messages BEGIN
  INSERT INTO messages_fts(rowid, text) VALUES (new.rowid, new.text); END;
CREATE TRIGGER IF NOT EXISTS messages_fts_ad AFTER DELETE ON messages BEGIN
  INSERT INTO messages_fts(messages_fts, rowid, text) VALUES('delete', old.rowid, old.text); END;
CREATE TRIGGER IF NOT EXISTS messages_fts_au AFTER UPDATE OF text ON messages BEGIN
  INSERT INTO messages_fts(messages_fts, rowid, text) VALUES('delete', old.rowid, old.text);
  INSERT INTO messages_fts(rowid, text) VALUES (new.rowid, new.text); END;
-- dopo la creazione (o se mancava un trigger):
INSERT INTO messages_fts(messages_fts) VALUES('rebuild');
```

(`messages` usa `INSERT OR IGNORE` e non aggiorna mai `text`: i trigger restano coerenti; la pulizia cancella con `DELETE`, che attiva `messages_fts_ad`.)

## 3. Registro delle regole di conservazione [WP0]

In `S/store.py`. `purge_step` diventa guidato dai dati, **con la stessa semantica di oggi** (stessi limiti per passo, stesse chiavi in `PurgeStep.deleted`, stesso limite di spazio).

```python
@dataclass(frozen=True)
class RetentionRule:
    name: str                      # unico, es. "messages", "messages_broker"
    table: str                     # tabella (costante del codice, mai input)
    where: Callable[[dict, float], list[tuple[str, tuple]]]
        # (impostazioni, now) -> lista di (clausola WHERE, parametri); lista vuota = niente da fare.
        # La clausola e' testo costante del codice; i valori passano SOLO dai parametri.
    counted_as: str | None = None  # chiave di PurgeStep.deleted a cui sommare le righe (None = non contate)

def time_rule(name: str, table: str, setting_key: str, unit_s: float = 86400,
              counted_as: str | None = None, extra_where: str = "",
              column: str = "time") -> RetentionRule
    # clausola "<column> < ?" [+ " AND (<extra_where>)"], parametro now - settings[setting_key]*unit_s

BUILTIN_RETENTION_RULES: tuple[RetentionRule, ...]
def register_retention_rule(rule: RetentionRule) -> None
    # aggiunge in coda; stesso nome e stessa regola = nessun effetto; stesso nome e regola diversa = ValueError
def retention_rules() -> tuple[RetentionRule, ...]   # predefinite + registrate, in ordine
CAP_TABLES: tuple[str, ...] = ("packets", "positions", "messages")  # erose dal limite di spazio, in quest'ordine
```

Esecuzione di ogni clausola: `DELETE FROM {table} WHERE rowid IN (SELECT rowid FROM {table} WHERE {clausola} LIMIT ?)`; `full` se una cancellazione raggiunge `limit`.

| 2 | `positions` | positions | `time < now − retention_positions_days` | `positions` |
| 3 | `telemetry` | telemetry | `time < now − retention_telemetry_days` | `telemetry` |
| 4 | `links` | links | come positions | — |
| 5 | `metrics` | metrics | come telemetry | `metrics` |
| 6 | `stats_hourly` | stats_hourly | come telemetry | — |

### 4.2 Agganci del Runtime (`S/app.py`)

```python
@dataclass(frozen=True)
class MessageMeta:
    event: MeshEvent | None   # evento che ha prodotto il messaggio; None = messaggio registrato da MeshLens (invio)
    outcome: str              # "new" | "dup" | "local"  (Ingestor.last_outcome al momento, "local" se event is None)
    @property
    def live(self) -> bool    # event is not None and outcome == "new" and not event.replayed

MessageHook = Callable[[dict, MessageMeta], None]
EventHook = Callable[[MeshEvent, str], None]          # (evento, esito "new" | "dup" | "ignored")

@dataclass(frozen=True)
class PeriodicTask:
    name: str
    interval_s: float
    fn: Callable[[], None] | Callable[[], Awaitable[None]]
    first_delay_s: float

class Runtime:
    message_hooks: list[MessageHook]
    event_hooks: list[EventHook]
    periodic: list[PeriodicTask]
    def add_message_hook(self, fn: MessageHook) -> None
    def add_event_hook(self, fn: EventHook) -> None
    def add_periodic(self, name: str, interval_s: float, fn, first_delay_s: float | None = None) -> None
        # first_delay_s None = interval_s. Coroutine function -> _every_async, altrimenti _every.
        # Solo prima di start(): dopo -> RuntimeError("Task periodico registrato dopo l'avvio").
```

Semantica (vincolante):
- `on_message` (in `build()`) chiama, **dopo** `bus.publish` e `notifier.on_message`, ogni `message_hook(msg, meta)` in ordine di registrazione. Viene chiamato per **ogni** messaggio che l'ingestione pubblica: testi ricevuti (`meta.live` vero solo al primo arrivo dal vivo), copie RF di un testo già visto da MQTT (`outcome == "dup"`), rigiochi S&F (`event.replayed`), invii propri radio/MQTT (`event is None`, `outcome == "local"`, `msg["direction"] == "out"`). Chi reagisce ai messaggi (bot, avvisi per parola chiave, webhook) filtra con `meta.live and msg["direction"] == "in"` e, se serve, `msg["from"] not in ctx.radios.local_ids()`.
- L'evento corrente è tenuto in una pila (le chiamate annidate di `on_event`, es. i rigiochi S&F, ripristinano il precedente).
- `on_event` chiama ogni `event_hook(ev, outcome)` per i `MeshEvent` (non `RawPacket`, non `kind == "storeforward"`) **dopo** ingestor, copertura, statistiche e registro pacchetti.
- Ogni aggancio è in `try/except Exception`: l'errore va nel log (`log.exception("Aggancio %s fallito", nome)`) e non ferma l'ingestione né gli altri agganci.
- `start()` crea un task per ogni `PeriodicTask` (con `_every`/`_every_async` esistenti, l'errore di un giro non uccide il task); `stop()` li cancella con gli altri.
